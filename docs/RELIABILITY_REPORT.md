# Clinical analytics reliability implementation report

Historical snapshot from 2026-10-17. For the current ingestion-only EDA workflow, see `EDA_WORKFLOW_SIMPLIFICATION.md`; statements below describing analysis-time EDA reflect the previous implementation.

Date: 2026-10-17. This report distinguishes exercised local behavior from deployment readiness. The configured live MySQL account rejected authentication, so a full study-data run and the production migration were not completed.

1. **Summary.** Extended the two existing workflows with bounded stage outcomes, deterministic result and quality gates, safe targeted recovery, optional Redis result caching, clearer clinical notices, and owner-scoped saved PDFs. The default workflow now refuses invalid results before EDA, insight, or charting. Report text no longer claims certification or filters that the run did not establish.
2. **Architecture found.** `app.main:app` serves the default Clinical Workspace, MySQL-backed analytics, ingestion, and Report History. `app.governed_app:app` is a separate study-scoped LangGraph API using an operational SQLAlchemy store and SQLite checkpoints. Human plan approval, SQL AST safety, insight validation, clinical templates, audit logs, and PDF history already existed. The default graph lacked reliable persistent resume and result-quality gates.
3. **Files modified.** Core paths: `app/api/{analytics,reports}.py`, `app/workflow/{graph,state}.py`, `app/analytics/{query_executor,sql_generator,followup_service}.py`, `app/ingestion/{quality_checker,mysql_loader}.py`, `app/database/{models,schema_service,session}.py`, `app/reporting/{history,pdf_generator}.py`, `app/governed/{analysis,api,report,service,store,workflow}.py`, `app/main.py`, `app/schemas/{analytics,reports}.py`, `requirements.txt`, `requirements-governed.txt`, `.env.example`, Clinical/Technical Workspace and report components, API types/client, tests, and documentation.
4. **Files created.** `app/analytics/{result_validator,eda,cache}.py`, `app/workflow/{reliability,runtime,recovery}.py`, `app/visualization/validation.py`, `app/reporting/{validation,safe_pdf}.py`, `scripts/migrate_report_quality.py`, `tests/test_reliability.py`, `frontend/src/components/Clinical/WorkflowNotice.tsx`, its test, and this report/checklist. Old unsupported PDF-rendering code was removed from `pdf_generator.py`.
5. **Files removed.** No source file was removed. One temporary edit helper was deleted after use.
6. **Database changes.** `ClinicalReport.analysis_metadata` is a nullable JSON field added by an idempotent, additive migration; the migration preserves existing rows. Governed reports now persist generated bytes in the existing `clinical_reports` entity. The authenticated default path reuses existing workflow operational tables for saved state. No clinical source table was modified. The migration was tested against SQLite fixtures but not applied to live MySQL because authentication failed.
7. **API contracts.** `POST /analytics/run` accepts `analysis_id`, `state_version`, and `action` for owner-bound approval, retry, quality decision, or stop, and returns stage/quality fields. `GET /analytics/runs/{analysis_id}` reads a saved owner-scoped run. `POST /analytics/report/pdf` can use `analysis_run_id` to render only server-saved validated outputs; standalone legacy submissions remain labelled as unverified source submissions. `POST /analytics/report/approve` now requires an owned completed `report_id` and records review acknowledgement, not certification. Report details include quality metadata. Downloads return original stored PDF bytes.
8. **Redis.** Redis is optional and only stores validated result rows. Configuration is `REDIS_URL` and `REDIS_TTL_SECONDS` in `.env.example`. Missing or failed Redis falls back to MySQL. Redis never stores recovery state or reports.
9. **Cache identity/invalidation.** Keys hash user identity, selected tables, dataset versions, schema, question, plan, SQL, parameters, and cache format version. Missing dataset versions bypass caching. Entries carry expiry and a payload digest; corrupt or stale entries are rejected and evicted. TTL and changed context invalidate eligibility. Real Redis availability was not tested here.
10. **EDA.** Deterministic checks report shape, nulls, blank/whitespace/specified sentinels, data types, numeric distribution and outliers, categorical frequencies, temporal ordering, exact duplicates, and grain-key duplicates where a contract defines a grain. Warnings have severity, impact, affected fields, and a continuation decision. No source data is imputed, dropped, or rewritten. Full domain-specific cross-table/cardinality checks depend on approved relationship and grain metadata and remain limited for unspecified datasets.
11. **Result correction.** SQL result contracts check expected columns, homogeneous values, finite numbers, required fields, AE denominators, and grain. A structural mismatch can trigger bounded SQL regeneration with feedback, re-execution, and revalidation; every attempt is recorded. Unsafe SQL, missing required data, or exhausted corrections stop. Generic query-result patching and automatic clinical data repair are intentionally absent.
12. **Retry/recovery.** Stage wrappers provide `SUCCESS`, `RECOVERABLE_FAILURE`, `USER_DECISION_REQUIRED`, `TERMINAL_FAILURE`, or `CANCELLED`, sanitized messages, allowed actions, and bounded retries (`WORKFLOW_MAX_RETRIES`, `RESULT_MAX_RETRIES`, each capped at five). Authenticated main runs save owner-bound snapshots and resume the failed stage when the source schema/version still matches. Upstream retry clears dependent outputs and quality approval. The governed path preserves checkpoints and narrows recovery similarly. One API worker is the supported deployment mode; distributed locking is not implemented.
13. **Clinical notices/review.** The Clinical Workspace shows concise stage failures, EDA warnings and retry/stop actions. Human plan approval and quality-warning acceptance are separate; acceptance cannot bypass mandatory SQL/result validation. Review decisions are audited. The report UI acknowledges review of a specific stored PDF; it does not represent clinical certification.
14. **Report History.** Existing `clinical_reports` rows remain the source of truth. Pending, completed and failed states are explicit; PDF bytes are validated before marking completed. Search, filter, details and owner-bound downloads use saved records. EDA findings and provenance are stored with reports. A failed save never returns a completed report claim.
15. **RAG.** Active `app` and `frontend/src` paths, dependencies and example environment have no RAG retrieval, FAISS loading, or embedding-model initialization. LangGraph remains. Older documents that mention retrieval are historical explanation only; active diagrams omit it.
16. **Architecture documentation.** `docs/architecture.mmd` and `docs/architecture.svg` now show AI generation separately from deterministic gates, approval, correction, cache fallback, report persistence, recovery and terminal states. README, deployment notes and implementation document were updated.
17. **Tests executed.** Focused backend pytest suite, broad backend pytest suite, frontend Vitest suite, frontend TypeScript/Vite build, SQLite migration fixture, PDF parsing, Poppler PDF render, and visual inspection of generated A4 pages.
18. **Exact results.** Focused backend suite: 59/59 passed (`reliability-final.xml`). Final frontend rerun: 23/23 passed; TypeScript/Vite production build succeeded. Broad backend suite: 64/69 passed, five failed on live MySQL-dependent paths because the configured account was rejected with error 1045. PDF fixture rendered and was inspected after a chart metric correction.
19. **Not executed.** The entire 335-case collected pytest suite was not run: evaluation cases include live services and model judging without configured access. Real MySQL end-to-end analysis, production report migration, real Redis hit/miss integration, and a live clinical-user acceptance session could not run without service credentials or availability. These are not claimed as passed.
20. **Limitations.** The broad suite still has five database integration failures in this environment. Join-cardinality diagnosis is strongest when approved keys/grain are known; it is not a general domain inference engine. Follow-ups have safe validation and current-result propagation but do not have a separate durable, stage-targeted retry API. PDF rendering retries bounded I/O failures without creating a second report; persistence failures are explicit but are not automatically retried. No independent clinical or regulatory validation is claimed. Existing frontend bundle-size warnings remain.
21. **Manual steps.** Provision a working MySQL account and approved dataset versions; run `scripts/migrate_report_quality.py` with migration privileges against the main report schema and, if different and pre-existing, the governed operational schema using `REPORT_MIGRATION_DATABASE_URL`; configure bearer-token grants and protected environment variables; optionally start a private Redis and set its URL; start the chosen API and frontend per README/DEPLOYMENT; rerun the five live MySQL checks and real Redis integration checks before accepting a production clinical deployment.

## Unresolved serious-adverse-event data discrepancy

Investigation recorded 2026-10-17. The focused test `tests/test_clinical_sql_generator.py::test_serious_adverse_events_result` expects 2,518 serious adverse-event records, but the configured MySQL database returns 2,517 for the approved predicate `AESER = 'Y'`.

The bundled `data/clinical_trials/AE.csv` contains 2,518 rows with `AESER = 'Y'`. The copy inside `Dataset.zip` has the same SHA-256 hash as the bundled CSV. The discrepant primary key is `USUBJID=STDY001-9999`, `AESEQ=1`:

| Source | AETERM / AEDECOD | AESER | AEREL |
|---|---|---|---|
| Bundled AE.csv | Serious Infection | Y | NOT RELATED |
| MySQL `ae` | Injection Site Reaction | N | RELATED |

The project-documented database setup and migration loaders read and insert CSV values directly; neither documents an `AESER` transformation. No trigger was found on MySQL `ae`. The database registry records an AE.csv load with 10,000 rows but does not preserve a source hash or row-level load history. The available evidence therefore does not establish which record is authoritative or when/how the database diverged. This discrepancy remains unresolved. Reconciliation requires confirmation from the dataset owner before any source or database correction; no clinical records, CSV files, SQL, or test expectations were changed as part of this investigation.
